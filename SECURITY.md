# The shell's rules

Oerba's pages are not trusted with the computer. The window they run in is built so that a page that went wrong, or a link that
leads somewhere it should not, finds nothing to reach. The rules are in `src/policy/` and tested without Electron; `src/shell/hardening.ts`
only wires them in.

- **Settings of every view:** `contextIsolation` on, `sandbox` on, no `nodeIntegration` (also not in workers or subframes), no `webviewTag`
  (a `<webview>` attach is refused), `webSecurity` on, no insecure content.
- **No bridge for remote pages.** No preload is given to Oerba's view, to the dev panel's preview, or to any page but the app's own three, the bundled setup screen, the update window and the
  dev panel's bar. The setup preload exposes three calls (`getState`, `onState`, `act`), the update window's own three of the same names, and the bar's three (`getState`, `onState`, and `act`,
  which is Close or `devices` and nothing else: `devices` asks the main process to pop the device picker, and carries no device), through `contextBridge`. Each does nothing unless it runs in its own page's top frame, and the main process checks the sender (for the bar, its
  very web contents and its top frame's address) again on every message.
- **What Oerba's page may ask of the app** (0.6.2, `src/policy/desktoplink.ts`). One thing, with no bridge: Oerba's view's User-Agent ends `OerbaDesktop/<version>`, by which
  Oerba draws a Dev Panel button, and its press opens `oerba-desktop:dev-panel`, with at most `?workspace=<owner>/<name>` in On-Demand's own pattern. The window handler takes
  that address before the link-out rules and under the link-out gate (below): only from Oerba's own top frame, just after a key or mouse press in the window, one ask for each
  press, a few a minute; any other address of the scheme, or one from anywhere else, is refused and recorded. It opens or closes the dev panel as the menus' Dev Panel does, and,
  for a workspace named that is one of the person's own running workspaces and whose Metro the last read of On-Demand saw listening, opens its app in the panel as the menu's
  Open in iOS Simulator does. It can do nothing the person's own menus cannot, and nothing in a workspace's frame can ask it. The other way, the app tells Oerba's page whether the
  panel is open by one of two fixed scripts (an `oerba-desktop` event whose `detail.devPanel` is true or false), run only in a page of Oerba's own, which hold nothing any page
  or workspace said. Since the token is in the User-Agent, a workspace's frame and every server Oerba's page reaches can see that the app is there and its version.
- **Navigation.** The setup view's main frame may only be the bundled setup page. Oerba's view's main frame may only be `https://app.oerba.dev`
  (no other port, no credentials in the address). Its subframes may be `https://*.oerba.dev` (Oerba frames workspace doors on those names). Everything else, including
  redirects, `file:`, `data:` and `javascript:`, is refused. A contents the app did not name may go nowhere.
- **Links out.** `window.open` never makes a window of ours. An `https:` address (with a host, no credentials) opens in the system browser with
  `shell.openExternal`, and any other scheme is dropped, but only when Oerba's own top frame asked for it, just after a key or mouse press in the window, one link
  for each press, and at most five a minute. A frame inside Oerba's page (a workspace door runs a developer's code) can never open the browser or send the page away:
  its requests are dropped and recorded. Electron does not say which frame called `window.open`, so the frame holding the focus stands for it. A plain link out of Oerba's
  page, if it is `https:`, goes to the browser under the same rule and the page stays. The app's own scheme (above) is taken before these rules, under the same gate, and never
  leaves for the browser.
- **No downloads.** Every download in every session is cancelled until a stage needs them.
- **Command-line switches.** A packaged app that finds any `-` switch on its command line beyond macOS's own `-psn_` refuses to start, with a dialog saying why
  (`src/policy/argv.ts`), so a launcher cannot loosen the shell with `--inspect`, `--no-sandbox` and the like. An unpackaged run is the developer's own and is not checked.
- **Permissions.** Every permission request and check is refused (media, notifications, geolocation, clipboard read, serial, USB, HID, Bluetooth and any kind not
  known), and so is every device permission. The `select-serial-port`, `select-usb-device`, `select-hid-device` and `select-bluetooth-device` choosers choose nothing.
  **One exception:** `clipboard-sanitized-write` (copy buttons) for `app.oerba.dev`'s own top frame, since writing text reads nothing.
  Devices are the app's own screens' to ask for one day, never a workspace's page.
- **Setup checks only read.** The only program run is Tailscale's `status --json`, by `execFile` with fixed arguments and no shell, and only its backend state is kept.
  Oerba is asked with a plain `GET /api/who`, no redirects followed, a timeout and a size limit.
- **The menu bar, notifications and badge only report.** They read `/api/now` and `/api/who` (a GET each, no redirects, a timeout, a 2 MB cap, a JSON object or nothing),
  never during setup. Since 0.6.0 they also ask On-Demand, by the same GET, which ports each of the person's own running workspaces is listening on (at most fifteen workspaces a read): its
  workspace record at `https://ondemand.oerba.dev/api/v2/users/<owner>/workspace/<name>`, the owner and name held to On-Demand's pattern first, for the id of the agent named `main`, which must be
  the shape of a UUID before it is put in the next address, `/api/v2/workspaceagents/<id>/listening-ports`. It is asked as the person, with no credential, as the forwards are (On-Demand takes the
  identity from the tailnet address): every one of these reads, `/api/now`'s and `/api/who`'s included, is made with `credentials: "omit"`, so no cookie or
  stored login of the app's session goes with it. Only the numbers are kept, in memory: TCP ports from 1024 to 65535, at most 32 a workspace, less databases' usual ports, which the forwards cannot carry, and (since 0.6.1) less the range Linux hands to programs that ask for no port, 32768 to 60999, where the workspace's own tools listen;
  a process's name, or anything else On-Demand says, is not. A workspace's code decides what it listens on, so it decides which numbers the menu offers, and nothing more: a number still meets
  every rule below before anything is dialled. Every item and every notification click only opens the window at a route of Oerba's page; none sends anything to Oerba or presses anything,
  **with one exception**: when Metro starts listening in one of the person's running workspaces (8081 or 19000, a port not listening at the read before, never at the first read after the app
  starts), a notification offers to open its app, and its click is the same as the menu's **Open 8081 in iOS Simulator** for that workspace and port (below), on the device last used for it,
  and so shows that app in the dev panel in place of whatever the panel was showing. A workspace can make that offer appear by listening on the port, so the offers are held: at most one a
  workspace in five minutes, and at most two a minute on a budget of their own, so that they never take the room of the other notifications. Only the person's click acts on one, and only
  while the last read still shows that workspace running with Metro on that port: a click after Metro stopped, or the workspace did (a notification stays in Notification Center), says so
  and runs nothing. A route is built from
  workspace and owner names that match a plain-name pattern, URL-encoded, and is checked again before it is put in the page's address, by changing only the hash. Every string from Oerba
  is cut to a length and reduced to plain printable characters (no control, bidirectional or private-use characters) before it reaches the menu, a notification or the badge.
  No bridge is given to any page for this. A global shortcut sends ⌘K to Oerba's own page with `sendInputEvent`, as a key press, and nothing else. The login item changes only when the person ticks it.
- **The localhost relay** (0.4.0, `src/relay/`). A forward is started only by the person, from the menu, for one of their own started workspaces and a port it listens on as On-Demand said (since 0.6.0; until On-Demand has answered, a port from a fixed list), and relays HTTP and websockets to `<port>--main--<workspace>--<owner>.ondemand.oerba.dev`.
  - *One exception to the link-out rule:* on the menu press that starts a forward of a web port (3000, 5173, 8000, 8080), the app opens `http://localhost:<the number it took>/` in the browser, an address the app builds itself and checks against the forwards running (`src/policy/browser.ts`: no other host, port, path or query); nothing a page, `/api/now` or a workspace says goes into it, and the rule for pages' links (https, from Oerba's own page, after a press) is unchanged.
  - *It listens* on `127.0.0.1` and `::1`, one number on both, and on no other address; a number another program already answers on, on either address, is skipped (binding beside another program's wildcard listener can succeed on macOS and would hide that program). It stops with its workspace (read from the poll of `/api/now`), when the person stops it, and when the app quits. At most sixteen at once, each holding at most 256 connections on each address (far above a dev server's page, low enough that a runaway local program cannot take the app's descriptors), at most 96 requests in flight (32 upstream sockets and about 64 waiting; more is answered 503), 15 seconds to connect upstream (then 502) and 300 seconds from connecting to the answer's headers (then 504; Metro's first bundle can take minutes), neither applying once headers have arrived (an event stream, a long download) or a websocket is up. An event stream counts toward the 96 in flight for as long as it is open, so a page holding many open on one forward fills that forward's own queue and no other's. A websocket has no idle timeout: Metro's hot-reload socket lives as long as the editor.
  - *It dials* only a name built from a port of four or five digits (1024 to 65535), a workspace and an owner each matching letters and digits with single hyphens inside (On-Demand's own name pattern), with the agent named `main` between port and workspace (On-Demand refuses a port's name with no agent; both of the lab's templates name theirs `main`, and `/api/now` does not say, so a template whose agent is named otherwise is not reached), at most 63 characters together, ending `.ondemand.oerba.dev`, over TLS on 443 with the certificate verified and the name as SNI and `Host`. The workspace and owner are checked against the ASCII shape on the raw string before any case change (`toLowerCase()` turns the Kelvin sign U+212A into `k`); capitals are On-Demand's own pattern and are lowered after. Nothing from a request chooses the name or the address (a request target must be a path: an absolute address, `*` and `//` are refused).
  - *It refuses* a request whose `Host` is not `localhost:<n>`, `127.0.0.1:<n>` or `[::1]:<n>` for its own number (DNS rebinding: a page at another name that was made to resolve to `127.0.0.1`), with 421; one whose `Origin` is present and is not `http://localhost:<n>`, `http://127.0.0.1:<n>` or `http://[::1]:<n>`, with 403, except that the `Origin` of another forward this app is running now **for the same owner and workspace** (a page on `localhost:5173` calling an API on `localhost:8000`, both of one workspace) passes, and so does `Sec-Fetch-Site: same-site` with such an `Origin`; a page of one workspace's forward cannot call another workspace's; and one with `Sec-Fetch-Site` of anything but none, `same-origin` or absent unless it is a top-level `GET` or `HEAD` navigation to a document, with 403 (On-Demand's own rule for when it believes a tailnet identity, `identityAllowedFor`). A websocket upgrade passes the same three checks before anything is dialled. A page on a localhost port the app is not forwarding cannot call a forward. A request with neither `Origin` nor `Sec-Fetch-Site` passes, since Metro, the Simulator and curl send neither; the relay can tell a browser's page apart only in a browser that sends Fetch Metadata: Chrome from 76 (Edge 79), Firefox from 90 and Safari from 16.4, macOS and iOS (MDN browser-compat-data for `Sec-Fetch-Site`). In an older browser a page's cross-site request carries no such header, and the `Host` and `Origin` checks, which every browser has, are what is left. A cross-site top-level navigation (`Sec-Fetch-Site` of `cross-site`, or `same-site` with no sibling `Origin`, with mode `navigate`; a dev server often changes state on a GET) is not forwarded: the relay answers with a small page of its own, "Opened from another site. Continue to localhost:<n><path>", whose link is absolute, `http://` and the `Host` the checks accepted, then the same escaped path and query (a target holding a backslash, or `%5C`, is refused with 400, since Chrome and Safari read `\` as `/`) (`Referrer-Policy: no-referrer`, `Cache-Control: no-store`, no cookie). Clicking it is same-origin and passes; an address typed in the bar or opened from a bookmark (`none`) goes straight through.
  - *It never sends on* `Origin`, `Sec-Fetch-*`, `Authorization` and `Proxy-Authorization`, On-Demand's `On-Demand-Session-Token` header, the query parameters `ondemand_session_token` and `access_token`, a client's `Forwarded`, `X-Forwarded-*`, `X-Real-IP`, `Tailscale-User-*`, `Referer`, `Expect` and the hop-by-hop headers, with any header the `Connection` header names. It holds no credential of its own. In place of a client's `Forwarded` it sends one of its own, `proto=http;host="<the loopback Host the client used, lowercased>"` (`localhost:<n>`, `127.0.0.1:<n>` or `[::1]:<n>`), made only from a `Host` of the loopback shape that the first check held to the forward's own number (and none at all otherwise), so that a dev server builds its addresses from where the request was really made: Expo's CLI does from SDK 58, and without it told Expo Go to fetch its bundle from `https://127.0.0.1:<n>`. On-Demand reads no `Forwarded` header (only `X-Forwarded-*`, `ondemandd/httpmw/realip.go`), and the lab's front door (Caddy, as configured on 24 Nov 2026) passes it through untouched, so it reaches the dev server alone and says nothing a local program could not say itself. `Authorization` and the two parameters are cut because On-Demand reads any of them as an explicit session token and then does not apply the person's tailnet identity (`hasExplicitToken`), so one would only break the request. `Cookie` is sent cut to the cookie names that workspace's own forwards have set through `Set-Cookie` (remembered in memory for each owner and workspace, at most 64 names, never written to disk, forgotten when the app quits), and without On-Demand's own cookies (`ondemand_session_token`, `oauth_state`, `oauth_redirect`, `ondemand_path_app_session_token`, `ondemand_signed_app_token` and any `ondemand_subdomain_app_session_token…`, the names `StripOnDemandCookies` drops). So another program's session cookie on another localhost port (a local admin tool's) never reaches a workspace. A `Set-Cookie` that deletes (a `Max-Age` of 0 or less, an `Expires` in the past) does not add its name. **This is not a wall between local programs.** Localhost's cookie jar is shared across ports, so a workspace that sets a cookie with the same name as another local program's replaces it, and a workspace that names such a cookie on a narrower `Path` can then receive that program's cookie of the name on requests under the path. The memory keeps out every cookie a workspace has not named, which is the common case. A workspace that fills the 64 names harms only its own pages. **Accepted:** the other direction is open. A cookie a workspace sets lands on `localhost`, whose one cookie jar is shared by every port, so other local sites see it; names are not prefixed, because that would break pages that read their own cookies in script. `Set-Cookie` comes back with any `Domain` attribute removed (so it lands on localhost) and without On-Demand's names. Responses are streamed, and a redirect to the app's own name is turned back to the forward's address.
  - *What it does not guard against.* Every program on the Mac, and the person's own browser at the app's name, already reaches those names as the person, because the tailnet address is theirs and On-Demand takes the identity from it for any request that is not another site's web page. The relay therefore gives local programs nothing new; its checks are against web pages in a browser, which could otherwise use a forward to read or write a workspace's dev server as the person. Programs that can set `Host` and `Origin` as they like (curl, a script) pass its checks, by design. So does an app in the iOS Simulator, which shares the Mac's network and whose requests (React Native's `fetch`) carry neither `Origin` nor `Sec-Fetch-Site`: a workspace's code that Expo Go runs there can call any forward, another workspace's included, and any local port, as a local program can. "A page of one workspace's forward cannot call another workspace's" holds for pages in a browser, not for that code.
  - *The self-test* may point the relay at a loopback `http` stand-in (`--relay-upstream`, an unpackaged app given `--selftest`, loopback only); a packaged app has no such flag, and `loopbackUpstream` accepts nothing but a loopback address.
  - Not done here: ports other than HTTP and websockets (a database, a debugger), which would hold an On-Demand session token and are a stage of their own.
- **Open in iOS Simulator** (`src/sim/`). Offered only on Metro's ports (8081, 19000), only from the app's own menu bar item and Dock menu, the offer when Metro starts (above), and the dev panel's device picker; and, since 0.6.2, Oerba's Dev Panel button for a workspace whose Metro is listening, after a press in Oerba's own top frame (*What Oerba's page may ask of the app*, above). No other page can start it. The menus' **Dev Panel** item (0.6.1) runs the same first part alone, the device list and a boot, and shows the device in the panel with no app, opening nothing in it. The panel's bar can ask for the picker and close the panel; the picker is a native menu the main process builds from `simctl`'s own list, read when the button is pressed, and a choice is held to a device that list named, for the workspace and port the panel is already showing, so neither the bar nor any page can name a device, a workspace or a port. A press starts the forward as above, then runs these and no other, each by `execFile` with an absolute program, fixed words, no shell, a timeout (15 s; 30 s for the device list; 120 s for a boot to finish) and a 4 MB output cap: `/usr/bin/xcode-select -p`, `/usr/bin/xcrun --find simctl` (the first so that a Mac with no developer tools at all is not offered an install by `xcrun`), `/usr/bin/xcrun simctl list devices --json`, `/usr/bin/xcrun simctl boot <udid>` and `bootstatus <udid>` (only when the device to use is shut down: the one chosen in the picker, or the one the panel shows, or the one last used for that workspace, or for Dev Panel the one the panel last showed, or, with none of those listed, when no iOS device is booted), `/usr/bin/open -b com.apple.dt.Devices devices://device/open?id=<udid>` (Device Hub, Xcode 27's replacement for Simulator.app) and, only if that fails, `/usr/bin/open -b com.apple.iphonesimulator --args -CurrentDeviceUDID <udid>` (Simulator, Xcode 26 and earlier), each found by bundle id and never by name or by the `devices:` scheme alone, since any app can register a scheme (the link is built from the UUID-shaped UDID alone); a bundle id is not proof that the app is Apple's, since a copy claiming it could be placed by a program already running as the person, and what it would receive is a UUID, `/usr/bin/xcrun simctl get_app_container <udid> host.exp.Exponent`, and `/usr/bin/xcrun simctl openurl <udid> exp://127.0.0.1:<port>`.
  - *The only variable parts* are a UDID, which must be the shape of a UUID and comes from `simctl`'s own list on this Mac (a device whose UDID is not one is dropped; a remembered or chosen UDID is only a preference, used when that list names it), and a port, an integer from 1 to 65535 that the app's own forward took. The address is built from those alone. Nothing a workspace, Oerba's API or a page said reaches a command: the workspace's and owner's names are used for the forward and the notification's words, never an argument.
  - *It changes one thing on the Mac:* it may boot an iPhone simulator that was shut down. It never erases, shuts down, creates or deletes a simulator, and installs no app, Expo Go included (it says where to get it). One press runs at a time; a press while one runs is ignored. The sandbox and entitlements are as they were: the app runs Apple's own tools as the person, which any program of theirs may do.
  - *What it opens to a workspace.* Expo Go runs the workspace's bundle on this Mac's network, inside the Simulator. That code reaches what a local program reaches (the relay's *What it does not guard against*, above): every forward and every port on `127.0.0.1`. The person chose to run that workspace's code by pressing; a workspace never starts it.
  - *The device each workspace was last opened on*, and the one the panel last showed (`src/sim/remember.ts`, 0.6.0; the panel's since 0.6.1), are kept in `devices.json` in the app's data folder, mode 0600, written whole by rename: at most 200 entries, each an owner and workspace in On-Demand's pattern, a UUID-shaped UDID and a device name of at most 60 printable characters, and anything else in the file is read as nothing. It is a preference and never an argument: a press uses it only when `simctl` still lists that device. Another program running as the person can change the file, and so choose which of the person's own simulators the next press uses, which it could do with `simctl` itself.
  - *The self-test* replaces the runner with a recorder (`simulator.run`), so the smoke run boots nothing, and gives the device memory a file in a scratch folder of its own, removed when it quits, so a run never touches the person's; it replaces On-Demand's ports with a stand-in and, outside it, reads none. The packed app has none of this code (the pack check looks for the recorder's device and the scratch folder's name).
  - Since 0.5.0 the sequence does not open Device Hub: once the address is open, the device is shown in the dev panel. Device Hub was then opened, by the same two commands, only by the bar's **Pop out**, which the bar has not had since 0.5.2, so the app opens Device Hub nowhere (the commands remain only for a press without the panel, which the app does not make).
- **The dev panel** (the iPhone panel until 0.6.0; `src/sim/serve.ts`, `server.ts`, `panel.ts`). It shows Expo's serve-sim (`@expo/serve-sim`, 0.14.6, Apache-2.0, pinned in `package-lock.json` with its integrity) beside Oerba's page.
  - *What runs.* serve-sim's command, from the app's own copy (packed at `Contents/Resources/serve-sim`, outside `app.asar`, because its native addon is loaded from a file and the simulator loads its libraries by path), in an Electron utility process of the app (Electron's Node; the `RunAsNode` fuse stays off). It runs as the person, unsandboxed, as any developer tool they start does: this is a trust in Expo's code at that version, which the lockfile pins and the packed app carries as shipped but for one change of Oerba's, marked at the head of the file it changes: serve-sim opens Device Hub in the background each time it starts, and Oerba's copy does not (`CHANGE` in `scripts/stage-serve-sim.mjs`; the build stops if a new version no longer holds the text it changes). The copy is byte for byte as reviewed (its files are pinned by digest, `PINNED` in `scripts/stage-serve-sim.mjs`, checked as they are staged and again in the packed app by the release build), its binaries re-signed with the app's identity. Its words are fixed: `--require-token --host 127.0.0.1 --single-device <udid> --disable clipboard --disable-share <udid>`, the UDID held to a UUID's shape. It is given no port: given one, it would try that port alone and stop when it is taken; given none, it takes the first free one from 3200 to 3249 on loopback and says which, and the panel reads it from that line. Its environment is built, not inherited (Electron's `utilityProcess` replaces the environment with the one given, as a probe on Electron 44 showed): a fixed `PATH`, `HOME`, `TMPDIR`, `USER`, `LOGNAME`, `NO_COLOR`, and `DEVELOPER_DIR` when it is an absolute path; nothing else of the app's environment reaches it, since serve-sim reads variables that would load further libraries into the simulator (`SERVE_SIM_ADDITIONAL_DYLIBS`, `SERVE_SIM_SIMPB_DIR`) and `simctl` passes every `SIMCTL_CHILD_*` on to the simulator's apps. One runs at a time, for one device. It is started only by the person: after a press of Open in iOS Simulator has opened the address, or by the menus' Dev Panel item, which shows a device with no app, or by the Dev Panel button of Oerba's own page after a press there (above); no other page, and no bridge or IPC, starts it. A packed app that is not in Applications (run from its disk image, or moved by macOS to a random place) does not start it, and the bar says to move it: serve-sim names a library inside the app to the simulator, and that path must last.
  - *Its door.* It listens on `127.0.0.1` alone, behind its own token gate. The token it mints is read from the first `Local:` line of its output (`Local: http://localhost:<n>/?token=…`, held to its own characters; nothing it prints later moves it), kept in the main process's memory, and given once to the panel's preview as `?token=`, which serve-sim turns into a cookie of its origin and a redirect that drops it from the address. **serve-sim also writes it to disk**, in its state file `$TMPDIR/serve-sim/server-<udid>.json` (mode 0600), under the Mac's per-user temporary folder, whose path has a random part. Its `/healthz` and `/readyz` are open by its design and readable from any page by CORS: `/readyz` says whether it is ready and names the device's UDID. Everything else needs the token: a page in a browser on this Mac, a workspace's forward included, reaches nothing more. **What the token buys** is serve-sim's whole API for that device, the preview's own powers: its exec channel (which also checks a browser's `Origin` and takes only its preview's) launches, installs and stops apps, uploads files, reads files from an app's data folder and some host folders (`file.readBase64` within its allowed roots), shows a file in the Finder (`reveal`) and changes settings; and since an iOS Simulator app is a process of this Mac, **installing an app is running native code on this Mac as the person**. So the token is worth as much as a program running as the person.
  - *The preview's view.* Its role (`simulator`) lets its top frame be serve-sim's page at exactly `http://127.0.0.1:<the port it took>` while it runs, and nothing else; it may make no frames; it has no preload; its session is its own (`oerba-iphone-panel`, in memory only), so serve-sim's cookie never meets Oerba's and is gone when the app quits; every permission, download and new window is refused, as for every view; and its requests may reach serve-sim's origin alone (`previewRequestAllowed`: `http` and `ws` to that host and port, its `blob:`s and `data:`), so were a string the workspace's app controls (its logs, its labels) ever to run as script in serve-sim's page, it could send the token nowhere. WebRTC's own traffic is not a request and is not filtered. So its screenshot button and its logs' Download save nothing, and its logs' Copy cannot write the Mac's clipboard. Text pasted into the panel goes to the simulator's clipboard, where the workspace's app can read it.
  - *What it changes on the Mac, while it is open.* serve-sim adds its loader (`libServeSimCapabilityLoader.dylib`, from the app's copy) to the simulator's `DYLD_INSERT_LIBRARIES`, so every app started in that simulator loads it, for the whole session. Closing the panel, closing the window (which only hides it; the app stays in the menu bar), quitting (which waits up to ten seconds for it, so it can hold a logout or shutdown that long) and restarting for an update each stop serve-sim with SIGINT, and it takes the loader out again; a close during a start stops what starts; if serve-sim stops by itself, the preview and the origin it was allowed go at once; if it is killed instead, the next start takes out what was left, and rebooting the simulator clears it. Its clipboard button, the first time it copies, installs serve-sim's `ServeSimPasteboard.app` into the simulator and grants it the pasteboard there. serve-sim loads nothing into the Mac's own apps. Its own controls can also shut down or reboot the device it shows. Its DevTools route, reached only with the token, fetches Chrome's DevTools front end from Google.
  - *Left out of the packed copy* (`scripts/stage-serve-sim.mjs`): network capture (a proxy that reads apps' traffic and adds its own root certificate to the simulator's keychain), its network library, camera injection, its middleware build and sources. The release build checks the copy is as staged, its scripts and other files byte for byte as reviewed, and that every binary in it carries the app's own Team ID; the unsigned pack check (`verify-pack.sh`) checks all but the signatures (`scripts/lib-pack.sh`, `assert_serve_sim`): the helper runs under the hardened runtime with library validation on, so nothing signed by anyone else would load.
  - *What it does not guard against.* A program already running as the person can read the token from the app's memory or from serve-sim's state file, or reach the simulator by `simctl` directly, as it could before. The app in the simulator is the workspace's code, which the person chose to run (above); **it runs as a process of this Mac, as the person, and whether that code can read the Mac's own files is not yet settled here.** If it can, it could read serve-sim's state file (were it to find the temporary folder's random path) and so take the token, and it could read the person's other files too, the token apart: that would be a property of running a workspace's code in the iOS Simulator at all, since 0.4.2. Until it is settled, open in the simulator only workspaces whose code you would run on this Mac.
- **Fuses, set in the packed app** (read back by `npm run verify:pack`): `RunAsNode` off, `EnableNodeCliInspectArguments` off, `EnableNodeOptionsEnvironmentVariable` off,
  `EnableEmbeddedAsarIntegrityValidation` on, `OnlyLoadAppFromAsar` on, `GrantFileProtocolExtraPrivileges` off, `EnableCookieEncryption` on. With the last off, a page inside `app.asar` does not load by
  `file://` at all, so the app's own pages (setup, update and the panel's bar) are served by a scheme of the app's own, `oerba-app://app/`, registered standard and secure, from a fixed list of nine files
  (`src/policy/bundled.ts`); a page cannot ask it for anything else in the package.
- **Sandbox, single instance.** `app.enableSandbox()` before anything starts. One instance holds a lock; a second launch only shows the first one's window and its arguments are never read.
  Screen and window recording requests (`getDisplayMedia`) are refused.
- **The self-test is not in the packaged app.** The packaged bundle is built with `__SELFTEST__` false and syntax simplification on, which removes the self-test, its stand-ins and its flags from the code;
  `npm run verify:pack` searches the packed `app.asar` for their strings. Tests and scripts are not in the package at all (only `build/app/` is packed), and electron-updater is bundled into `main.js`.
- **Signed with the hardened runtime**, under the owner's "Developer ID Application" identity, found in the keychain by its kind (no name, hash or team is written here), and notarised with notarytool through a
  keychain profile, then stapled. The only entitlement is `com.apple.security.cs.allow-jit`, which V8 needs to compile JavaScript at run time; `disable-library-validation`,
  `allow-unsigned-executable-memory`, `allow-dyld-environment-variables` and every device or file entitlement are not given.
- **Updates come by themselves, and what is not this app's next version is refused.** electron-updater runs with `autoDownload` and `autoInstallOnAppQuit` off; the app's own Updater (`src/update/`) downloads a version once it has found it plain (three numbers, no prerelease tail), then checks the zip before anything installs it: it must hold this app's bundle alone, whose own `Info.plist` names this app and the version the feed offered, newer than the one running (`updateZipRefusal`, `src/update/zip.ts`). Only then is it handed to Squirrel.Mac, and the update is ready only once Squirrel.Mac has taken it; from then any quit installs it, and a day later the app restarts into it when the person is away. A version whose download or check failed is not fetched again by itself for a day. Nothing a page says reaches any of it. **What this does not guard against:** with no press needed, a build that is validly signed by the same team and is a newer version (a stolen signing identity, or a compromised build of the app's own) is installed as surely as a genuine one; a press never guarded against that either, since the person sees only the version the feed claims. The feed is the `publish` setting of the build (GitHub, `Oerba-Labs/oerba-desktop`), written
  into the app as `app-update.yml`; the app never calls `setFeedURL`, and nothing from a page or the command line reaches it. What refuses a forged update is **TLS to GitHub** (the feed and the zip are fetched
  over it) and **Squirrel.Mac**, which installs a new app only if its code signature satisfies the running app's own requirement (signed by the same team's Developer ID). electron-updater refuses a zip whose SHA-512 differs from `latest-mac.yml` (`npm run tamper` proves it with electron-updater's own code: the download ends in `ERR_CHECKSUM_MISMATCH`, nothing is left in its cache and `update-downloaded` never fires); that guards a corrupt or truncated download, but the sum comes from the same place as the zip, so it proves nothing about who made it. A feed that lies about both is met by Squirrel.Mac's signature requirement, which only a signed build can prove, and nothing here does. Release notes are shown as plain text (`textContent`), tags and entities stripped.
  The update window has its own three-call bridge, given to it alone.
- **Packing downloads tools, and uploads nothing.** `npm run pack:unsigned` (and the release build) makes electron-builder fetch its helper tools (icons, 7zip, dmgbuild) from GitHub, without any credential;
  it sends nothing anywhere. Only `scripts/release.sh` talks to Apple, by notarytool, for the owner's own build.
- **The self-test override** of Oerba's address needs both an unpackaged app and an explicit `--selftest` flag, and accepts only a loopback `http` origin.
- **The app holds no secret** and names no address that is not public.
